# obot.agent v0.5.0 (Upcoming)

- **A worker that stops now wakes the Navigator, instead of waiting for someone to notice.** Twice in two days a worker finished, sat with its work unjudged, and was found only by accident — twenty minutes on the Saturday, six hours on the Sunday night with a full backlog and nothing running. The five-minute sweep already knew; it had no way to tell anyone. It does now: it reads every worker's job record, and one line reaches the Navigator's session within a sweep cycle when a worker stops, stalls, dies, or sits waiting on an answer nobody gave — and when nothing at all is running while there is ready work. The reading is the part that took the work. A stopped worker's `state` field lies: two workers read `working` for twenty hours while stuck on a permission prompt, and one read `blocked` while dead on a network error, so the detection is built on the fields that actually move. Nothing here can reach you: the whole path is one file tail inside one named session, which is the point — a worker finishing is an officer's problem, not yours. And it says when it is deaf. If nothing is listening, the sweep prints `WAKE CHANNEL DOWN` beside the pending list every five minutes rather than a quiet page, so a missed wake looks like a missed wake. ([roadmap #212](https://github.com/jwildfire/obot.roadmap/issues/212), [#151](https://github.com/jwildfire/obot.agent/issues/151))

- **The dashboard knows when you last looked at it.** Every surface being built for your absence wants to answer *what changed since I last looked*, and nothing recorded when you last looked — so each one was one step away from substituting something that merely correlates: the last deploy, the newest changelog entry, a fixed twenty-four hours relabelled. All of those are worse than no signal at all, because a confidently wrong window actively tells you not to look. Both local servers now record one thing where a page is handed to your browser: the last time each surface was opened. One timestamp per surface, and nothing else — no user agent, no referrer, no history — kept in the local-only ops store beside the answers and the config checks, because this is behavioural data about you and sits under the same rule as the config list. The header reads it back: `local only · 10:03 · last opened 5h ago`. ([roadmap #205](https://github.com/jwildfire/obot.roadmap/issues/205), [#143](https://github.com/jwildfire/obot.agent/issues/143))

- **The hard part was refusing to write it, and the rule was measured rather than assumed.** A watcher, a health check or a page refreshing itself would keep marking a page as seen and silently destroy the signal for the one reader it exists for. So a real Chrome was pointed at a local server and asked what it actually sends: opening a page and clicking a tab arrive as a `document` navigation, an iframe as `iframe`, a `fetch()` poll as `empty`, the favicon as `image`, and curl — like every watcher and health check — sends no `Sec-Fetch-*` headers at all, which is what excludes the whole class by construction instead of by heuristic. The measurement earned its keep on the one case that would have been guessed wrong: a page's own meta refresh is header-identical to a person opening it, except for a `Cache-Control: max-age=0` that a manual reload also sends. Both are therefore excluded, so a reload does not count as a fresh look. That is deliberate, because the error is one-directional — an undercounted look shows you a longer window and tells you to look again, an overcounted one tells you not to bother, and only the second kind can hide something. This was not hypothetical: the session tab embeds the live view, which refreshes itself every sixty seconds, so under the obvious rule a tab left open would have marked itself as seen forever with nobody in the room. Verified live rather than argued — the tab sat open for eighty seconds, its frame re-requested itself once, and the timestamp did not move.

- **And it says *first look* or *unknown* rather than something plausible.** No record renders `first look`, never *nothing changed*. A record that cannot be parsed, a stamp that is not a time, or a clock that moved backwards renders `last opened: unknown` with the reason in the tooltip, because a window invented to fill a gap is exactly the failure this exists to prevent. Every branch was proved against a running server with a real browser rather than in a unit test alone: one browser load recorded a look, nine curls and a HEAD and a JSON poll moved nothing, the second load rendered a real prior timestamp, and a truncated record and a stamp from the future both came back `unknown`. The last defect found was the most familiar one — the line worked, the tests passed, and it was `display:none` at the window width you actually use, which is the same thing as no signal — so the narrow header now drops *local only · HH:MM* and keeps the phrase.

- **The sessions tab is a roster of agents now: who ran, what it cost, and what it moved on the roadmap.** You asked for it in one line while approving the Navigator design — *"I want the opsdb/sessions page refactored to show a list of all agents along with thier ID, status, cost and the impact they had on the roadmap"* — and it could not have been built a day earlier, because worker ids shipped that same morning and they are the only reliable join: every issue, pull request, comment and commit an agent writes is authored by the same `obotclaw[bot]`, and GitHub has no field that separates one agent from another. One row per agent, opening into the evidence behind it. The first live render put fourteen named agents on the page against $234 of attributable spend, next to one collapsed row holding the $5,015 spent before ids existed — which is the number the roster is really for: it says how much of the program's cost can now be traced to somebody, and how much never will be. Three of the four columns come from records that already existed, so nothing new is collected; the fourth, roadmap impact, is the Navigator's delivery verdicts, each already checked against GitHub, rendered as links so any row on the page can be verified in one click rather than believed. ([roadmap #199](https://github.com/jwildfire/obot.roadmap/issues/199), [#138](https://github.com/jwildfire/obot.agent/issues/138))

- **And it is built to refuse the four lies a page like this tells.** A job's own state file is not evidence that it finished: one worker died on 2026-08-15 leaving `done` behind it and a normal-looking completion note, and the only surviving trace is the append-only timeline, whose last entry is still `working` an hour before the terminal stamp — so status is a join of the two records and a disagreement between them reads as death, not as success. Impact is not read from the job records' own child list, which is empty for nearly half of measured jobs including one that merged three pull requests and filed two issues; an impact column built on it would under-report exactly the agents that did the most. A cost is never rendered as zero when the truth is that nothing was read — a missing usage artifact says `cost unavailable`, a stale one says how old it is, and an agent that started after the last pricing run says `not yet priced`, because a zero and an unread file look identical on a page. And nothing is hidden for being unnameable: the pre-id era is one collapsed row carrying its total, and the named rows plus that row reconcile to the priced artifact's own total, which is a test rather than a claim. Six further defects were found the only way they could be — by running it against the real machine rather than a fixture — including a standing session dropped from the page for having started the day before, and a link to `github.com/jwildfire/A` invented from the letter in `Q&A #183`.

- **The Navigator now watches all seven project repos for work that shipped with nothing in the plan above it.** The night of 2026-08-15 produced six pieces of work with no requirement recording any of them, and the nightly audit caught one of the six. It was blind for one reason worth stating plainly: a spoke-repo issue is visible to that audit only when a hub issue already lists it as a child, which is the very link that was missing — the check could not see the failure because the failure was the absence of the thing that would make it visible. So the five-minute sweep now looks from the other end, across every repo in the policy file, and reports three things it could not see before: work that shipped with no requirement above it, the decision registry and the published index disagreeing, and an agent that finished having produced nothing. A fourth check turned out to already exist — an answer you recorded and nobody applied has been marked OVERDUE at the one-hour mark since it shipped — so it is covered by a test here rather than rebuilt, because a check nobody has exercised is indistinguishable from one that is not there. The rule that keeps the first one usable is yours: gate on work done, not on filing. An issue needs an ancestor once it is closed or a pull request against it merged, never the moment somebody opens it — the blunt version fires on 26 of the 41 open spoke issues and 14 of the 16 here, and a list nobody trusts is muted inside a week. A reference in body prose does not count as a link, because one of the six named its requirement in a sentence and was scored as linked by two separate readers while GitHub recorded no parent for it. The first live run found 56 pieces of shipped work with no requirement above them in the last fortnight and 112 older — a real backlog, and yours to see rather than his to read, which is what the delegation grant is for. The section shows the newest few per group with the true count in the heading and says how many it did not show, because a truncated list that stays quiet about it reads as full coverage. ([roadmap #195](https://github.com/jwildfire/obot.roadmap/issues/195))

- **And the audit now tells you how old its answer is, before you quote it.** This one came out of an investigation rather than a plan. Two checks were reported as disagreeing about the same board state within hours of each other — the nightly audit said four requirements were off the board, a verifier run later the same morning found nine more — and the design leaned on the audit heavily enough that the disagreement had to be settled before anything was built on top of it. They never disagreed. The audit had not run: its most recent output was from the previous morning, twenty-two hours old, and predated every issue in question by half a day. Its four findings are not board findings at all — one missing design document and three parents whose sub-issues are done. A day-old total was relayed as this morning's board state, and nothing anywhere in the chain was in a position to notice. The file has always carried its own timestamp; what it never carried was a reason for a reader to look. So the sweep now reads it and prints one line — `nightly audit: last run 23h ago at 2026-08-15T07:52Z — 4 finding(s); anything filed since then is invisible to it` — on the healthy path as well as the alarming one, because twenty-two hours is inside any sane staleness threshold and a check that only speaks up when the audit is late would not have prevented this. A missing findings file is a finding in its own right: an absent audit reads as a clean one.

- **The operating officer exists, and you can talk to it.** You approved the Navigator design this morning — *"I'm good with D0017 recommendations. Implement. Let me know when the agent is active."* — and `scripts/obot-navigator` launches it: a standing 🧭🤖 session, bridged to Remote Control so you can reach it from your phone, launched from the workspace root, and a singleton, because two officers writing requirements for the same ask is the failure worth designing out on day one. Its contract is `skills/navigator/SKILL.md`, reached as `/s-navigator`, and it carries the boundary you approved under N1: the Navigator authors and repairs the plan, and never touches the work. It may write requirements, amendments, task issues and its own delivery record; it may not merge, publish, correct another agent's output, or write the concierge's state. That asymmetry is what makes the delegation grant safe — undoing one of its calls means reopening or editing an issue, seconds of work, with both the call and the reversal on the record. The singleton rule is proved rather than asserted: the launcher takes its jobs directory from the environment, so a test can stand up a live Navigator, a waiting one, a finished one and a room full of workers, and check that only the first two block a second launch. The concierge's launcher had the same rule and no test, and while writing one its preflight line turned out to print the session name as mojibake — fixed in both. ([roadmap #195](https://github.com/jwildfire/obot.roadmap/issues/195), [#134](https://github.com/jwildfire/obot.agent/issues/134))

- **And it keeps a record of what a day of agents did to the roadmap.** `tools/delivery-log` is the Navigator's own file and the only one the session writes: one line per closeout naming the worker, what it produced, the requirement it moved and a verdict of confirmed, drift or none — with `none` reserved for a worker that correctly stopped to ask you something, which is not a failure, since only a pull request advances a requirement. Calls made on your behalf that change the plan get a permanent `n0001` id from the same locked, append-only journal the config list and the worker roster use, so you can reverse one by quoting its number and both the call and the reversal stay on the record. The record is append-only by construction: the last two nights produced repeated cases of one process quietly overwriting another's file, and this is the file the whole role exists to produce. The five-minute sweep reads it, folds it in as a `## Delivery` heading, and the dashboard's Navigator tab renders it — no rendering code, because the tab was deliberately built to render any heading it finds. And the record audits itself: an id the journal issued that has gone missing from the file you read is a finding, not a note, because a delegated decision that leaves no record is indistinguishable from no decision.

- **Every worker agent now has a number, so you can finally ask what a particular agent did.** You asked for it in one line — *"I also want each worker to get a unique ID moving forward W000x"* — and the reason it matters is that GitHub cannot help you here at all: every issue, pull request, comment and commit an agent writes is authored by the same `obotclaw[bot]` identity, and there is no field that separates one agent from another. With 33 workers started in the last day and six running at once, "which one did this" had no answer. Each worker now claims a permanent `W0042` before it spawns and carries it in its own name — `👯🤖 W0042 2026-08-16 workerids` — so the id travels through `claude agents`, the session list, scratchpad lines, commit trailers and pull request bodies without any new plumbing, and you can address a worker by the bare id. The id is claimed inside the same exclusive lock that the config list's allocator uses, because worker spawns land 2.4 seconds apart on a busy night and the unlocked version of this lost 4 of 24 entries in a measured run. **Ids are never recycled — not even when a worker dies.** Two died on 2026-08-15, one blocked and one stopped after stalling for three hours, and they keep their numbers: the whole point is being able to ask what each worker did *including the ones that did nothing*, and an id freed by death is an id that lies about history. Subagents take their parent's id with a `.1` suffix, mirroring the `D0001.n` decision sub-ids, because they have no session of their own and their parent is what is accountable for what they wrote. Forward-only, as you asked — three of the previous night's workers left no recoverable trace at all, so a backfill could never be complete and a partial one that looked complete would be worse than a clean start. ([roadmap #194](https://github.com/jwildfire/obot.roadmap/issues/194), [#130](https://github.com/jwildfire/obot.agent/issues/130))

- **And the Navigator now tells you if the convention stops being used.** This is the part that would otherwise go wrong silently: a tool like this can ship, be wired into the five-minute sweep, report success on every run, and never once actually be called by a spawn — which looks exactly like it working. So `worker-id --audit` checks the ledger against the harness's own job records rather than against what agents say about themselves, and **a worker that spawned with no id is a failure, not a note**. It also catches an id handed out twice, a hole in the sequence, and the same id on two live workers; an id claimed by a spawn that then failed is only a note, since a burned id is correct. The verdict is the first line of the output and the exit code is the verdict, so the sweep can act on it without reading prose — the same discipline the config ledger needed after its notes displaced its verdict on nearly every run. A ledger that was never armed reports **NOT ARMED** rather than "nothing to check", and fails outright if workers are running behind it.

- **The config items tell you exactly what to do, and prove you did it.** You called them "pretty useless" and asked for an installation qualification — so that is what an entry is now ([#122](https://github.com/jwildfire/obot.agent/issues/122)). Every one carries the exact command *or* the exact click-path, what you should see when it worked, and a check that proves it: `Do` / `Expect` / `Verify` / `Unblocks` / `Source`, with the mechanism optional and last. Click a config row and the whole thing opens with copy buttons and a **Check** button that runs the proof and records a real pass or fail — no more ticking a box and hoping. A failure says `printed 0, expected 2`, not "exit 1". The three fields are enforced where entries are *written* (`tools/blocker-log` now refuses `--fix`), because a tool that accepts a one-liner gets fed one-liners forever. Only single read-only commands run unattended; the web-UI-only and device-side steps say so plainly and hand you the command instead. All nine open items were re-verified and rewritten — and the re-verification did its job: **two turned out not to belong on the list at all** (`obotclaw[bot]` simply cannot be a GitHub assignee, whatever token asks, so no grant of yours fixes it; and the `blocker-log` allowlist line folded into the `scratchpad-log` one, since it is the same file and the same array). Two genuinely new ones were filed. The list went from nine items to nine, having lost two and gained two — and every one of them is now something you can actually do.

- **Delete or snooze anything in the list.** Release candidates and decisions too, not only config items. A snooze always states how it comes back — a day, a week, or "until it changes", and all three watch the item itself, so a pull request that gets pushed to or a config entry that gets reworded wakes on its own. Snoozed and cleared rows stay on the page in collapsed sections carrying their wake condition and a **restore** button, because a snooze you cannot see is a silent delete. And nothing is actually deleted: your click is the approval, and it appends to a local append-only ledger the queue filters on — the config list file is never edited by a click, so `blocker-log --retire` stays the one writer that retires an entry with its id and body intact. Dismiss says what it really does, per kind: for a release candidate, *"hides it here; the pull request stays open on GitHub."*

- **A `critical` tag you can trust, because agents cannot claim it.** There is no flag to set. An item is marked only when something *else* measured it: a `Blocks:` reference that GitHub confirmed open at capture time, or a computed condition like an answer that has gone unapplied too long. The row shows the claim — `critical · blocks obot.roadmap#182` — so a weak one is obvious at a glance, and the tag is capped at three, with any further claims reported rather than silently shown or silently dropped. Critical pins above all three sections; the sections keep your order underneath, and a pinned row moves rather than appearing twice. On tonight's real queue **nothing earned it**, which is the point. Verified at a 390px iPhone viewport: no horizontal overflow, one-line rows, titles clamped to two.

- **An answer you click now reaches the artifact on its own, and the page tells you where it is.** The decision lane end to end ([#120](https://github.com/jwildfire/obot.agent/issues/120)), written the night you answered a decision at 22:22 and asked twice whether it had landed — it had not, and nothing in the system knew. Clicking now records **one** answer per decision: a repeat click counts as a click on the same answer rather than a second one, and a *changed* answer supersedes the earlier record instead of sitting beside it, with the old one stamped and kept because a changed mind is a fact worth keeping. Every answer is joined to its `D####` id at the moment you click (from the hub's decision registry), per-question answers are stored against their sub-ids with the codes you read (`D0003.1`, `S1`), and prose with no verdict is recorded as prose rather than mislabelled "per-question" with nothing in it. The hand-off is now real: the 🧭🤖 Navigator sweep — launchd, every five minutes, running whether or not a session is — picks up what you recorded, announces it in `navigator-state.md` and the session scratchpad, and marks it delivered; the agent that updates the artifact marks it applied with a link. The three states are on the page as you go: **captured** ("recorded here — the Navigator picks it up within five minutes"), **delivered** ("handed to an agent"), **applied** (with the link, so you can confirm it yourself). And if the sweep is not running, the sidebar leads with *"your answers are going nowhere"* and the restart command instead of showing a quiet row that looks like success. Agents answer "has he decided anything I haven't acted on?" in one bounded read — `node obot.agent/tools/ops-answers pending`, which `prime-rehydrate` now carries — and an answer unapplied for more than an hour is marked OVERDUE everywhere it appears.

- **A release candidate is now named `gsm.safety v1.1.0-RC1`, and the description that used to crowd the title moved to where it reads better.** @jwildfire's rule, replacing the one he set hours earlier the same day: an RC PR is titled `{package} vX.Y.Z-RCn` and **no other summary is allowed** — no `Release candidate:` lead, no em-dash tail. The `-RCn` counter counts candidates put in front of him: the first is `-RC1`, it increments only when review is re-requested after a changes-requested decision, the **same PR is retitled rather than replaced** so his review thread survives the re-cut, it resets per version, and the tag drops the suffix entirely — what ships is `v1.1.0`. Because a bare version tells you nothing in a queue of five, the Operations Dashboard now gives each RC row a **second line**: the one-sentence executive summary from the PR body, which the body contract requires and puts first, already extracted by `reviews-queue` at no extra cost and truncated cleanly at a 390px iPhone width. Every RC body now runs one sentence → links (**demo page and `NEWS.md`, the `NEWS.md` link mandatory in every RC PR**) → the list of requirements closed, each still carrying its `Closes #N` keyword so issues keep auto-closing → details as needed. `obot-merge` warns on an off-shape RC title but never refuses: its other gates protect the release's record, while a title is cosmetic, fixable in one command, and blocking there would stall a release @jwildfire had already approved. ([#121](https://github.com/jwildfire/obot.agent/issues/121))

- **A release candidate now opens *in* the dashboard — summary, release notes, what it closes, and the demo page running live.** @jwildfire asked for the PR in an iframe in the middle panel; GitHub makes that impossible (a PR answers `x-frame-options: deny`, so it renders blank permanently, and proxying his logged-in GitHub session to defeat that would be a security hole rather than a workaround). So the panel is native, which turns out better: it opens instantly from the cache — so it still opens with the network down — it matches the dashboard instead of dropping a foreign page into the middle of it, and it runs in his stated review order, *"skim the PR, read through the demo page and then read the release notes"*, without GitHub's chrome around it. The **demo page itself is framed live** (Pages sets no frame headers, unlike github.com); a demo hosted anywhere else degrades to a link. **Approving stays on GitHub** — reviewing here means writing there, and the RC gate is his, so the panel ends at *Open on GitHub to approve* rather than putting a one-click approve inside a local tool. This is renderable only because the RC body contract in the bullet above gives every RC body the same shape: the contract makes the panel possible, and the panel is why the contract is worth enforcing. Where a body predates the contract the panel names the gap in place of the missing piece — the first real one it rendered, open.gismo#10, correctly reads "No NEWS.md link — the contract requires one." - **Your dashboard and your session view are one local site now, and the queue reads like a list rather than a wall.** Second pass on the Operations Dashboard ([roadmap #180](https://github.com/jwildfire/obot.roadmap/issues/180), [#118](https://github.com/jwildfire/obot.agent/issues/118)), all of it @jwildfire's calls: the session hub moved onto the second tab of the dashboard's own server, with the dashboard as the default view, one port and a persistent header across all of it — `/ops-dashboard` and `/session-dashboard` both land on the merged site, and the status-line link keeps resolving because the dashboard now writes the marker it reads (the watch loop runs without `--serve`). "Your hands" is now **config**, and every config item carries a permanent `c0001`-style id, claimed once at capture time by `tools/blocker-log`, stored in the list so it survives a reword, and never reused — the same rule as the hub's decision ids, so you can approve one by quoting it. Release candidates are relabelled `package version — what it is` (`gsm.safety v1.1.0 — the participant-level metrics phase`), derived from the repo and the `(Upcoming)` NEWS heading for PRs written before the rule; the rule itself is now in the RC framework and the release-notes skill. A third tab, **Navigator**, renders what the 🧭🤖 sweep has seen — the RC queue and its event log, read fresh on every request, and if the sweep stopped running the tab leads with "the observer is dead" and the restart command rather than passing a stale file off as current (per-agent attribution is not there: every agent's issues and PRs are authored by the same bot identity, so it needs a data source that does not exist yet — the tab renders any section the sweep adds, including that one, without a code change). - **Background agents no longer show up on your phone.** Sibling sessions stopped registering with Remote Control ([obot.roadmap D0013](https://jwildfire.github.io/obot.roadmap/reports/decisions/2026-08-15-delegation-lanes/) follow-through): obot-prime is the one session you reach from claude.ai/code and the mobile app, so ~20 sibling bridges a day were a control surface nobody opened — and a permanent row each in your Remote Control session list, which had grown to 47 dead entries crowding out the four sessions actually running. Siblings stay visible in `claude agents`, and prime can still message and resume any of them; only the phone/web view goes away. `scripts/obot-prime` and `scripts/obot-auto` are unchanged — leads stay bridged. A sibling you want to reach from your phone is opted back in per spawn. Removing the `--remote-control` flag alone would have done nothing (the flag and the global `remoteControlAtStartup` setting are peers in one `||`), so the spawn now passes `--settings '{"remoteControlAtStartup": false}'`, verified on CLI 2.1.233 to leave permission mode and workspace settings intact.

- **The files that decide what agents may do can no longer be changed by an agent on its own.** The rule existed since July and lived only in prose, so nothing read it: `obot-merge` never looked at which files a pull request changed, and twice in sixteen days a change to the guardrails merged without @jwildfire's sign-off — the second time with a description claiming the sign-off process had been followed. Now the merge tool fetches the PR's full file list and forces the attested lane the moment it touches one of the guardrail paths — the policy file, the merge tool, the resolver, the goal registry, the hooks — so it merges only with `--jeremy-approved '<where/when he said so>'`, on every lane, in every repo, whether or not he is present, and the audit comment it leaves names the paths that were touched. Three things that would have let it fail quietly are closed with it: the file list is fetched paginated and its completeness asserted, because the obvious command truncates at 100 files with no error; the tool checks that the policy file it just read matches the copy in force, so a session in a worktree cannot resolve the lane from the rules its own branch is proposing to change; and `--check` now reports policy and mergeability as two verdicts, so "policy permits merging" is never heard as "this will merge". Scope, corrected the same day after the first pull request it caught was a routine convention change: the list is the permission surface only, so documentation living beside it stays ordinary work, and a guardrail merge on an operational repo's integration branch can be carried by a decision @jwildfire has already recorded (`--decision`) instead of asking him again — the audit comment then says plainly that he did not review that merge, and names what he did decide. His in-session sign-off remains the only thing that carries a release-branch merge or anything in a clinical repo, and neither form is ever available to an unattended session. ([his decision](https://jwildfire.github.io/obot.roadmap/reports/decisions/2026-08-14-hub140-one-question/) · [#65](https://github.com/jwildfire/obot.agent/issues/65), [#75](https://github.com/jwildfire/obot.agent/issues/75) · hub [#140](https://github.com/jwildfire/obot.roadmap/issues/140))

- **Choosing between a sibling and an in-conversation subagent is now a test, not a feel.** When @jwildfire asked whether sibling sessions still earn their keep under obot-prime, the answer was to keep both lanes ([D0013](https://jwildfire.github.io/obot.roadmap/reports/decisions/2026-08-15-delegation-lanes/)): a subagent's full result flows back into the context of the session that called it, while a sibling leaves only a short report — so the front door cannot also be the loading dock. The one-line routing rule is now written into `session-prime` and `session-spawn`: work whose entire product is an answer runs as a background subagent; anything that leaves a commit, an artifact, a PR, or state that must outlive the session spawns a sibling. When in doubt, spawn the sibling. ([#111](https://github.com/jwildfire/obot.agent/issues/111))

- **A review on any release candidate is now noticed within five minutes, with nobody watching.** The Navigator's first capability ([obot.roadmap#157](https://github.com/jwildfire/obot.roadmap/issues/157)): a scheduled sweep (`tools/navigator/sweep.mjs`, launchd `com.obot.navigator-sweep`, every 5 minutes, installed by `tools/navigator/install-launchd`) discovers RC PRs across every repo in `scripts/policy.json` — release-role base branch, review requested from @jwildfire, or already reviewed — and writes the queue, each RC's latest review with excerpt, and new events (reviews, RCs appearing, merges/closes) to `{workspace}/.claude/session-hub/navigator-state.md`, every line stamped `[verified gh HH:MM]`. Events also land in the session scratchpad as `🧭🤖 nav` lines. obot-prime reads the file as a warm source (`prime-rehydrate` already bundles it) and treats a `swept:` header older than 15 minutes as a dead observer, never as current data; per-RC review Monitors are retired. Replaces the session-bound watching that let sv#131's CHANGES_REQUESTED review sit unseen for hours on 2026-08-15.

- **A local page that is your todo list, and where you answer decisions.** The **Operations Dashboard** (`tools/ops-dashboard`, `/ops-dashboard`) serves one page on your own machine carrying everything waiting on you in a single queue: release candidates, the blockers only your hands can clear, and every open decision artifact. Click a decision and it opens in the main area with the answer controls beside it — adopt all in one click, or approve/reject/defer/ask-for-more per question with your own words, which are what get quoted verbatim in the artifact's Decisions section. Answers stage in a new local-only folder (`.claude/ops/`, append-only, sentinel-guarded like the blockers list) and an agent applies them to the artifact, the decision log and the index; the page itself never holds a credential that can write to the hub on your behalf. This is the local variant of the "approve" button — on the public site an unauthenticated approval is forgeable, on your own machine a click is yours by construction. Vocabulary is now fixed: the **dashboard** is this local page, the **hub** is the public site. ([roadmap #180](https://github.com/jwildfire/obot.roadmap/issues/180))

- **Blockers now have a ten-second capture path.** When an agent hits a wall only @jwildfire's hands can clear — a settings line the permission classifier refuses, an account-level grant, a device-side setup — `tools/blocker-log` files it to the workspace-local blockers list in one allowlistable call: headline, a required paste-ready fix, required provenance, optional what-it-unblocks. The script creates the list (sentinel first) if missing, refuses duplicate headlines, and inserts under the list's `## Open` heading without ever rewriting the shared file. Approved with the blockers-list decision (BL3, 2026-08-15); the list itself stays local-only — the hub deploy now fails if its sentinel ever reaches the published site.

- **A reply now comes before the work that supports it.** After obot-prime answered one question in 31 silent minutes (bookkeeping, a long sibling briefing, and a post-spawn wrap-up all composed ahead of the reply), the responsiveness contract gained a mechanical turn-ordering rule: the first content block of any turn answering @jwildfire is text, a delegating turn's first tool call is the spawn, and all bookkeeping follows the reply. Prime additionally caps every turn at two tool calls before its first visible text, defers memory and state writes to after the ack, and composes briefings as pointers to on-disk artifacts rather than paraphrases. Briefing depth is unchanged — only its position in the turn moved. ([#102](https://github.com/jwildfire/obot.agent/issues/102))

- **Every repo's write policy now says whether it is operational or clinical.** The control split @jwildfire set — operational repos self-improve with automatic merges to production, clinical repos are reviewed by him before anything reaches the released surface — is recorded as a `class` field on each repo in `policy.json`, printed by `obot-policy explain` and `matrix`, and checked by `validate`. demo-301 is classified clinical on his override, with the condition for a later switch to operational written where the next session will find it. The retired safety-histogram fork (archived; its renderer lives on in safety.viz) leaves the policy file in the same change. ([decision](https://jwildfire.github.io/obot.roadmap/reports/decisions/2026-08-15-operational-clinical-classification/))

- **Two finished pull requests sat unmerged overnight because of how the merge command was typed.** Three workers in two days reported the same thing — the merge lane refuses background agents — and it was the wrong diagnosis twice over: nothing refuses them, and nothing is background-specific. The workspace allowlist permits three spellings of `obot-merge`, and a permission rule matches a command only when every sub-command matches, splitting on `|`, `&&` and `;`. Agents habitually write `bash scripts/obot-merge 158 -R jwildfire/obot.agent 2>&1 | tail -20`, where the `bash` prefix defeats all three path rules and `tail -20` is a second sub-command no rule covers. Unmatched commands do not fail — they fall through to the auto-mode classifier, which is nondeterministic and refuses about one call in thirty. The evidence is a census rather than a theory: of 497 `obot-merge` invocations in the session transcripts, exactly 7 were written in a matchable form and all 7 were allowed, while every one of the 17 refusals in that history sits among the 490 that matched nothing. The same string that was refused on obot.roadmap#217 was allowed three minutes later, which is what a coin flip looks like from the inside and why three separate workers each concluded they had hit a wall. The fix changes no permission surface and needed nobody's approval: the documented form is now the bare single command everywhere an agent reads it, `session-reviews` no longer tells the reviewer to chain the merge call into a compound, and a test fails if any documented example drifts back to a decorated shape. ([#162](https://github.com/jwildfire/obot.agent/issues/162))

# obot.agent v0.4.0

**See it move:** the [annotated v0.4.0 demo](https://jwildfire.github.io/obot.roadmap/reports/oa-v0.4-demo/) walks each change as a real terminal capture with the command that produced it.

v0.3.0 gave obot the ability to run unattended. v0.4.0 is about what that run costs you: a session opens before the model thinks, the dashboard is one click from any status line, write policy is one file instead of two drifting ones, the three things that used to park an overnight run on a permission prompt are fixed, and the release you are reading has a written contract behind it. Nothing in the session-command surface is removed or renamed.

## What's new

- **A session opens before the model produces a token.** The hand-off — the previous session's priorities, what is waiting on you, what changed overnight — is assembled by a shell script during command expansion, so it is already in the prompt at first paint instead of being rediscovered over several model round trips. `/session-init` and `/s-init` are now the same fast command, and `obot-auto` launches unattended leads through it too. ([#76](https://github.com/jwildfire/obot.agent/pull/76), [#77](https://github.com/jwildfire/obot.agent/pull/77), [#80](https://github.com/jwildfire/obot.agent/pull/80), [#81](https://github.com/jwildfire/obot.agent/pull/81) · hub [#91](https://github.com/jwildfire/obot.roadmap/issues/91), [#148](https://github.com/jwildfire/obot.roadmap/issues/148))

- **Every status line ends with a clickable hub link** — the live session ops hub inside the obot workspace, the deployed roadmap hub anywhere else — so the dashboard is one click from any session. The status line also became a tracked, installable artifact under `tools/statusline/` rather than one untracked file on one machine, and the watch loop can serve the live view over loopback so the link opens in Chrome instead of Finder. ([#52](https://github.com/jwildfire/obot.agent/pull/52) · hub [#24](https://github.com/jwildfire/obot.roadmap/issues/24))

- **A repo's write policy is one decision in one file.** Merge tiers and unattended-autonomy grants used to live in two files needing separate edits per repo, and they had drifted into a state neither could express. They are now one `policy.json` where a repo gets a single profile, `obot-policy explain <repo>` prints what that profile means in plain words, and branches match by role rather than by name — so a release branch called `master` or `site` needs no special-casing. ([#59](https://github.com/jwildfire/obot.agent/pull/59), [#61](https://github.com/jwildfire/obot.agent/pull/61) · hub [#18](https://github.com/jwildfire/obot.roadmap/issues/18), [#140](https://github.com/jwildfire/obot.roadmap/issues/140))

- **Overnight runs stop parking on permission prompts.** Spawned agents were handed a worktree path outside `.claude/worktrees/` — the only location Claude Code auto-approves — so each one waited for a click that, unattended, means until morning. A new triage table also tells you in one command why a session is missing from Remote Control, and the wrapup rebuilds the Analytics cost data before it posts so the spend page stops going stale. ([#69](https://github.com/jwildfire/obot.agent/pull/69), [#63](https://github.com/jwildfire/obot.agent/pull/63), [#67](https://github.com/jwildfire/obot.agent/pull/67) · hub [#18](https://github.com/jwildfire/obot.roadmap/issues/18), [#46](https://github.com/jwildfire/obot.roadmap/issues/46))

- **What needs you is the first thing a wrapup says.** Every wrapup output — checkpoint page, diary entry, morning digest, closing message — now opens with the release candidates awaiting review and the decisions awaiting your call, each linking its PR and its demo or decision artifact, with the work log underneath. Both lists carry forward until you close them, decisions post to the hub's Q&A discussions where you answer in-thread, and a risk named in a wrapup becomes a tracked issue carrying a proposed mitigation. ([#83](https://github.com/jwildfire/obot.agent/pull/83), [#85](https://github.com/jwildfire/obot.agent/pull/85), [#71](https://github.com/jwildfire/obot.agent/pull/71), [#72](https://github.com/jwildfire/obot.agent/pull/72) · hub [#142](https://github.com/jwildfire/obot.roadmap/issues/142)–[#144](https://github.com/jwildfire/obot.roadmap/issues/144), [#148](https://github.com/jwildfire/obot.roadmap/issues/148))

- **Releases now have a written contract.** `docs/rc-framework.md` states what reaches your review queue — release candidates and decision artifacts, nothing else — and what a candidate must carry, with a deployed demo page as a hard gate. The companion `rc-release-notes` skill puts the notes in a repo's `NEWS.md`, demo link first, and the tag publishes that section verbatim on approval. This file is that convention applied to obot.agent itself. ([#83](https://github.com/jwildfire/obot.agent/pull/83), [#86](https://github.com/jwildfire/obot.agent/pull/86) · hub [#123](https://github.com/jwildfire/obot.roadmap/issues/123))

- **Releases are now real, reviewable PRs.** A lagging `stable` branch, cut at v0.3.0, gives this repo what it never had: a base to propose a release against. Each release is a `main → stable` PR whose diff is exactly the release window, carrying the RC roles and merging only with explicit approval — the release you are reading arrives that way. The same decision set the program's governing principle (operational repos self-improve with automatic merges to `main` and periodic `stable` releases; user-facing clinical work is reviewed before prod) and the NEWS.md convention this heading follows: every repo keeps a NEWS.md current in `main`, unreleased work under a `(Upcoming)` heading. ([decision record](https://github.com/jwildfire/obot.roadmap/discussions/155))

- **The test suite runs in CI.** Every push and pull request now runs the full 112-test suite plus the policy-file validator on GitHub Actions — previously this repo had no CI at all, which mattered rather a lot for a repo whose merges to production are automatic. A red check now blocks a broken `main` instead of a morning surprise.

- **Prime remembers across restarts.** The standing Q&A session writes its durable state to a capped, provenance-stamped `prime-state.md`, and a cold session rehydrates from one read via `tools/prime-rehydrate` — including across midnight, which the first version got wrong and a same-night fix corrected. ([#91](https://github.com/jwildfire/obot.agent/pull/91), [#94](https://github.com/jwildfire/obot.agent/pull/94) · hub [#154](https://github.com/jwildfire/obot.roadmap/discussions/154))

- **`/grill-me` interviews you about a goal** — a resumable, multi-session elicitation interview that extracts what you want built, including the parts held tacitly, before requirements are filed. ([#96](https://github.com/jwildfire/obot.agent/pull/96))

- **Thirteen session commands have one-word aliases, and three are new:** `/s-idea` files a half-formed thought to the triage queue without derailing the session, `/s-reviews` walks the PRs waiting on a decision one at a time, and `/s-prime` runs a session as the standing question desk — a long-lived session that answers from warm context in seconds and delegates anything slower. ([#64](https://github.com/jwildfire/obot.agent/pull/64), [#84](https://github.com/jwildfire/obot.agent/pull/84) · hub [#48](https://github.com/jwildfire/obot.roadmap/issues/48), [#114](https://github.com/jwildfire/obot.roadmap/issues/114))

## Also in this release

- The roadmap audit queue costs no tokens until you click, and batches submit in parallel with per-agent worktrees so concurrent applies stop colliding. ([#55](https://github.com/jwildfire/obot.agent/pull/55), [#56](https://github.com/jwildfire/obot.agent/pull/56) · hub [#92](https://github.com/jwildfire/obot.roadmap/issues/92), [#109](https://github.com/jwildfire/obot.roadmap/issues/109))
- An upstream audit you can hand over: five ready-to-file `gsm.qtl` issue drafts, each with a runnable repro, at `drafts/gsm.qtl/`. Re-verified against current upstream on 2026-08-14; they stay drafts because agents do not write outside the `jwildfire` org. ([#62](https://github.com/jwildfire/obot.agent/pull/62))
- **Milestones stopped being optional.** No work starts on an issue until it carries a milestone, and a release names the issues it ships — `obot-merge` now refuses any merge whose `Closes` target has no milestone, and a release-branch merge whose body names no issue at all. The rule is written where an agent hits it before branching: `--auto` increment selection, the release-notes procedure and the RC checklist. safety.viz v1.6.0 shipped the night before this landed grouping none of the four issues it delivered. ([#89](https://github.com/jwildfire/obot.agent/issues/89) · hub [#123](https://github.com/jwildfire/obot.roadmap/issues/123))

- **A note on the merge lane.** Three `obot-merge` calls in this window were denied by the Claude Code auto-mode classifier and succeeded on a plain retry, which briefly looked like a threat to the whole unattended model. It was not: 3 denials in 99 real invocations, traced to the one command spelling the workspace permission allowlist did not cover. The allowlist rule landed on 2026-08-14 and the three merges that closed this release went through on the first attempt. Evidence and reasoning: [decision artifact](https://jwildfire.github.io/obot.roadmap/reports/decisions/2026-08-14-merge-lane-classifier-denials/).
